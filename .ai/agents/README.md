# 如何写一个任务域的知识文件

每个任务域(支付、多设备、i18n、部署……)一个文件,四段式结构。
**写之前问自己:这个域里,哪些坑是 AI 不提醒就一定会踩的?——那些就是你要写的内容。**

## 四要素

### 1. 不变量(这个域里,什么永远不能被破坏)

写成「违反即事故」的硬约束。示例:

```
- 金额计算必须使用最小货币单位(分)的整数,禁止浮点运算
- 所有对外接口的入参必须在入口处完成校验,下游信任上游
```

### 2. 危险地图(改哪些地方必须格外小心)

「改这里必须连带做什么」「这里的隐含时序是什么」。示例:

```
- 价格展示与订单结算两条链路各有一份折扣计算逻辑,改折扣必须双链路验证
- 提交弹窗 onClose 里同步打开下一个弹窗会顶掉队列——新增弹窗必须走统一队列
```

### 3. 回归清单(改完这个域,必验什么)

可执行的验收判据,不是「注意测试」而是「验证这两个场景」:

```
- 改折扣规则后:同一下单参数分别走「展示页」与「结算接口」比对金额一致
- 改弹窗后:连续触发两种弹窗,确认第二种不被顶掉
```

### 4. 判据(可执行的验收标准)

「违规为 0 才算完成」,而不是「注意质量」。
**反例必写**:Agent 最大的风险是创造性发挥,反例划出「不许发挥」的边界。

## 写作规范

1. **判据可执行**:每条都能变成一个验证动作;写不出验证动作的约束,先补度量再写
2. **一行顶一段**:提炼后的判据,不贴长篇事故描述——事故细节放链接
3. **真源指针化**:细节在别处时写指针(见 docs/xxx),不抄内容(抄一份漂移一份)
4. **反例标注事故来源**:让读者知道这条规则是血泪换的,不是审美偏好
5. **先轻后重**:一个域的文件从几十行起步,长出来而非设计出来
