# 任务拆解(五步法)

## 目标
把需求拆成「每个都带验收判据、验证步骤、授权级别、依赖关系的可执行单元」,按垂直切片组织,交付可测试的功能增量。

## 何时不使用(边界声明)
- 一次性探索/原型——目标本身就是试错,直接动手,但结论要沉淀成文档
- 单文件小改动且影响面清晰——列出改动点即可,不必走全流程

## 工作流

### 第 1 步:需求理解确认
- 先**复述你对需求的理解**,等用户确认边界——模糊需求在这一步消灭
- 禁止:理解有歧义就直接开始拆

### 第 2 步:影响面分析
- 检查 `.ai/danger-map.json`,列出改动可能触碰的危险区
- 输出影响面草稿(改哪些文件/模块/系统、跨不跨链路),**请用户确认并补充 AI 不知道的隐含依赖**

### 第 3 步:垂直切片与依赖图
- **反对横向切分**(先全部数据层 → 再全部接口 → 再全部 UI)——横向切完的每一层都无法独立验证,集成风险全部堆积到最后
- 按完整用户路径切:「用户可以注册账号(数据 + 接口 + 页面)」一片交付可测试功能
- 画出 ASCII 依赖图,标出哪些切片可并行、哪些必须串行:

  ```
  schema ──► API 类型 ──► 注册接口 ──► 注册页面
      └──► 校验逻辑(可并行)
      └──► 种子数据/迁移(可并行)
  ```

### 第 4 步:任务分解
每个任务强制携带**五件套**,缺一不可:

- **验收判据**(可勾选;写不出判据 = 继续往下拆)
- **验证步骤**(怎么验证:测试命令/构建命令/人工检查路径——两层验证纪律:自动化验证之外,标出需要真环境冒烟的部分)
- **授权级别**(四维度判定:失败可见性 / 影响面 / 验证覆盖 / 是否契约;命中危险地图 → 最高 human-led)
- **依赖关系**(显式编号引用)
- **规模估计**(XS = 1 文件 / S = 1~2 / M = 3~5 / L = 5~8 / XL = 8+ 必须继续拆)

**继续拆分的信号**(命中任一必须继续拆):
- 超过一次专注会话(约 2 小时)
- 验收标准超过 3 条
- 触及 2 个以上独立子系统
- 标题里出现「和」「并」「+」

### 第 5 步:排序与检查点
- 串行走依赖链,无依赖的并行
- 每 2~3 个任务设检查点:系统应可运行、构建通过
- 关键检查点:**与人工确认后再继续**

## 产物规范
- 计划写入 `tasks/plan.md`,任务清单写入 `tasks/todo.md`(项目指定外部 tracker 时,清单降级为条目 ID/链接的有序索引)
- **禁止覆盖未完成的计划**:目标文件已有未勾选任务时,同一工作就地更新;不同工作必须停下询问——未勾选任务可能正在另一会话执行,覆盖会摧毁别处不存在的工作
- **幂等写入**:重复执行先查重,禁止产生重复条目

## 反模式速查表(预判借口,逐条反驳)
- 「我会边做边搞」→ 混乱加返工,10 分钟规划省数小时
- 「任务很明显,不用写」→ 仍要写下——显式任务暴露隐藏依赖
- 「拆解是开销」→ 拆解本身就是任务
- 「AI 写的,直接能用」→ 两层验证纪律:自动化验证 + 真环境冒烟,缺一不可;失败语义必须贯通到 UI 最后出口
- 「先跑通再说,异常路径后面补」→ 失败分支与正常流程一起设计;验证矩阵要覆盖异常路径与不同时机
- 「旧计划过时了,直接替换」→ 未勾选任务可能正在另一会话执行——停下询问

## 红旗(开工前自查)
- 未写任务清单就开工
- 未经确认覆盖含未勾选任务的计划
- 任务无验收判据或验证步骤
- 任务全是 L/XL
- 无检查点;未考虑依赖顺序
- 验证只有「跑通了」,没有具体命令/路径

## 判据
- 每个任务五件套齐全,规模 ≤ L
- 每个切片单独可验证,切片间依赖显式
- 检查点已设置,关键节点有人工确认
- 计划与清单已落盘,且未覆盖他人未完成内容
